Java native obfuscator

A new, efficient Java native obfuscator.

RJNI parses compiled Java bytecode, translates eligible method bodies into Rust, compiles them into a native library for the host platform, and links that library back into your classes through JNI. Once a method has been through this process, its original bytecode no longer exists in the .class file — a decompiler has nothing to reconstruct it from.

Before and after

What a decompiler sees, before and after.

This is a small, deliberately readable example, not a substitute for evaluating RJNI against your own code. It shows one real, verified mechanism — nativization plus string encryption — not the full effect of every protection pass.

single-class example
Original — decompiled
package com.example.licensing;

public final class LicenseGate {

    public boolean isValid(String key,
                            long issuedAtMillis) {
        String prefix = "LIC-";
        long age = System.currentTimeMillis()
            - issuedAtMillis;
        return key.startsWith(prefix)
            && age < 31_536_000_000L;
    }
}
Protected — decompiled
package a;

public final class a {

    public native boolean a(java.lang.String,
                             long);
}
What moved where. LicenseGate and isValid were renamed. isValid's body — the comparison logic, the one-year threshold, and the "LIC-" literal — was translated to Rust and compiled into the bundled native library; the class file keeps only a native method declaration with no body to decompile. The "LIC-" literal itself is never embedded as plaintext in that library either — it was encrypted before translation and is decrypted at the call site at runtime.

Mechanism

How RJNI works.

One pass over your JAR, six stages, run in this order every time.

  1. 01

    Input and configuration

    You supply a built JAR, an optional trial fraction, optional class-level keep patterns, and an optional watermark string. Nothing about your build process changes beyond running RJNI as one extra step after packaging.

  2. 02

    Parsing and eligibility scan

    Every class is parsed and checked against the registered exclusion profiles (reflection-by-name, ServiceLoader, JPMS descriptors, proxy-framework internals, your own keep rules) and an interface check — an interface method can never legally be native. String constants are collected across the whole JAR so later passes know what's safe to rename.

  3. 03

    Bytecode-level protection passes

    Eligible classes are renamed; string literals are encrypted; private and closed-hierarchy member names are renamed; control flow is flattened into a dispatcher table where it's safe to do so. Each pass is independent and composable.

  4. 04

    Per-method translation

    Every remaining method body is exported to an intermediate representation and checked for translatability. A method using an unsupported bytecode shape is excluded with a specific, reported reason — never silently mistranslated.

  5. 05

    Native compilation and JNI relinking

    Every translatable method is compiled into Rust source and built into one shared native library for the JAR. Each method is flipped to native and bound through RegisterNatives, resolved against the correct class regardless of class loader.

  6. 06

    Finalisation and packaging

    Remaining (non-nativized) methods are wrapped for decompiler resistance; anti-tamper checksums and the anti-debug check are injected; matched resource files are encrypted; an optional watermark is embedded; the native library is bundled under a randomised, obfuscated path; RJNI's own runtime classes are renamed per build. The result is written out as a single, ordinary-looking JAR.

Specification

Protection capabilities.

as implemented today

Every row below is checked against this project's own build and decision log, not aspirational copy. Implemented means live in the pipeline and verified against real, unmodified third-party JARs. Where a feature has a real scope boundary, it's stated rather than smoothed over.

Bytecode-level protection
FeatureStatusDetail
Method nativizationImplemented Eligible method bodies are translated to Rust, compiled into the bundled library, and relinked through RegisterNatives. The class file carries a native declaration with no Code attribute.
Class name obfuscationImplemented Eligible classes are renamed into one flat, opaque package. A class referenced only by a string literal (Class.forName, ServiceLoader) is left unrenamed to avoid breaking the lookup.
Method & field renamingConditional Private members are always renamed. Non-private, non-static members are renamed only where the member's entire class hierarchy resolves inside the JAR being protected; any external supertype keeps the conservative, private-only slice.
String & constant encryptionConditional Every LDC string literal inside a method body is encrypted and decrypted at the call site. A static final String field's own compile-time constant is not covered — other classes may already have inlined its plaintext at their own compile time.
Control-flow flatteningConditional Branches and jumps are rewritten through a single dispatcher table. Constructors, methods with an existing exception handler, and methods where a value crosses a block boundary on the operand stack are excluded rather than risk incorrect bytecode.
Decompiler-resistant wrappingImplemented Every remaining method body is wrapped in a whole-method exception handler shaped to make common decompilers' control-flow reconstruction fail or render unreadable output, with no change to observable behaviour.
Native and packaging protection
FeatureStatusDetail
Native library bundlingImplemented The compiled library is stored at a random per-build path with a .dat extension, XOR-obfuscated so the raw bytes carry no recognisable native-binary header.
Loader & runtime hardeningImplemented RJNI's own bundled bootstrap classes are renamed per build into their own flat package, not shipped under a fixed, guessable name.
Anti-tamper checksumsImplemented Each protected class verifies its own bytes against a SHA-256 checksum in a separate bundled resource at load time, and fails loudly on a mismatch.
Anti-debug detectionConditional Detects a JDWP debug agent attached at JVM startup. Deliberately does not flag a general -javaagent — production APM/monitoring tools are common and this is scoped to avoid false positives against them.
Resource & asset encryptionConditional getResourceAsStream calls with a literal, statically resolvable path are redirected through a runtime decryptor. The URL-returning getResource form is not yet covered.
Build-time watermarkingImplemented An optional per-build identifier is embedded and recoverable from a jar file directly, without running it — for tracing a leaked copy back to its licence.
Build and evaluation controls
FeatureStatusDetail
Config-driven keep rulesConditional Exact-class, package-recursive (pkg.**), and single-package (pkg.*) patterns exclude matching classes from renaming. Member-level keep rules are not yet supported.
Trial / evaluation modeImplemented Protects a deterministic subset of eligible classes, selected by internal name rather than at random, so a trial output is reproducible across runs.
Framework exclusion profilesImplemented Built-in profiles cover reflection-by-name, ServiceLoader, JPMS descriptors, Spring's proxy internals, and the packaged internals of CGLIB, ByteBuddy, Javassist, and Hibernate's bytecode provider.
Multi-release JAR awarenessPlanned META-INF/versions/ variant handling is designed but not yet implemented.
Windows native-library cleanupPlanned The extracted native library is removed after load on POSIX systems. Windows delete-on-close cleanup is a documented no-op today.
Code signingNot planned RJNI's output is a library loaded in-process via System.load(), not a shell-launched executable — see Security model below.
Will it work for my project?

Compatibility.

The direct answer, before the FAQ: RJNI runs against ordinary compiled JAR files on the JVM, excludes what it can't safely translate, and leaves everything it excludes as ordinary bytecode rather than breaking it.

JDK and class files
Class file versionsMajor versions 52–70 — JDK 8 through JDK 26 — parsed and exported via ASM.
invokedynamicLambda and method-reference call sites (LambdaMetafactory) are supported. Other bootstrap methods, most notably StringConcatFactory-based string concatenation, are not yet translated.
Exceptions & synchronizationtry/catch, throw, whole-method synchronized, and generics need no special handling and are verified against real corpus code. Block-level synchronized(obj) { ... } is excluded from control-flow flattening.
Known bytecode gapsBitwise/shift operators, switch statements, unary negation, multi-dimensional array literals, and object reference-equality branches are not yet translated. An affected method is excluded from nativization with a specific, reported reason.
Platforms
Verified todaymacOS — the project's own development and verification platform throughout Phase 2, including a real, unmodified 1,200-class third-party JAR.
Design target — not yet independently verifiedLinux x86-64, Windows x86-64, Windows ARM64, and macOS Apple Silicon are the project's stable target tier; Linux ARM64 and Intel macOS are experimental. This is the documented build-target design, not a claim that every listed platform has been built and tested — cross-platform builds have not yet been independently produced outside the primary development machine.
Frameworks and reflection
Reflection by nameClass.forName callers are excluded from nativization automatically; a class referenced only by string is also excluded from renaming.
ServiceLoaderProvider-lookup classes are excluded automatically via a dedicated profile.
JPMSmodule-info descriptors are excluded automatically.
SpringYour own @Component/@Service-style classes stay eligible; Spring's own proxy-generation internals are excluded.
CGLIB / ByteBuddy / Javassist / HibernatePackaged internals of these proxy-generation libraries are excluded outright.
Kotlin interopExercised incidentally against a real Kotlin/Java-interop project, not a dedicated, separately tested target.
Other obfuscators (ProGuard, ZKM, Allatori, DashO)Layering order and output compatibility are not verified. Treat as unknown rather than assumed to work.
Build integration and deployment
Invocation todayRuns as a JVM application against an input and output JAR path. A packaged standalone CLI and Gradle/Maven build-tool plugins are planned, not yet shipped.
Deployment shapeDrop-in replacement JAR — same entry point, same public behaviour, runs on an ordinary JVM. Nothing about how you deploy or launch it changes.
Code signingNot required by this architecture — see Security model.
Stated plainly

Security model and limitations.

RJNI raises the cost of extracting logic from a shipped Java application. It does not claim to defeat a determined, well-resourced reverse-engineering effort against a native binary — no protection tool in this category can make that claim honestly, and it isn't made here.

Adversary tiers
TierCapabilityPosture
CasualRuns an off-the-shelf decompiler against the shipped JAR, no further effort.The primary tier RJNI is built to raise the cost against — nativization removes the method body a decompiler would otherwise reconstruct.
Motivated amateurReads native-library disassembly, uses javap/bytecode viewers, spends real time on strings and symbols. Partially raised: string/resource encryption and decompiler-resistant wrapping increase the cost here, without fully defeating this tier.
Determined reverserHas the native binary, a disassembler, time, and the skill to reconstruct logic from native code by hand. Explicitly out of scope. RJNI raises the cost of extraction; it does not claim to defeat a determined effort against the compiled native artifact.

Stated directly, not implied:

  • Nativization removes the Java method body available to ordinary bytecode decompilers — it does not make the underlying logic unrecoverable.
  • RegisterNatives is a name-based JNI API, so a nativized method's name and descriptor remain visible as plaintext strings inside the compiled native library — structurally unavoidable without abandoning JNI as the relinking mechanism.
  • Every obfuscation and encryption pass here raises the cost of a casual or moderately motivated attack. None of them is presented as unbreakable.
  • Native binaries remain analysable by a sufficiently capable attacker with a disassembler and enough time.
  • Anti-tamper checksums detect a class file edited in isolation after protection; they do not resist an attacker who edits the checksum resource and the class together, or who modifies a running JVM directly.
  • Anti-debug detection is scoped to JDWP specifically, to avoid false positives against legitimate production monitoring agents — it is not a general instrumentation or dynamic-analysis countermeasure.
