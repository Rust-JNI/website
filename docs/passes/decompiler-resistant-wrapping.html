Decompiler-resistant wrapping

ImplementedEvery remaining method body is wrapped in a whole-method exception handler, with no change to observable behaviour.

What it does

Every non-constructor method that still has an ordinary bytecode body — anything left over after nativization has taken what it can — is wrapped in a whole-method catch (Throwable t) { throw t; }. This was chosen over more aggressive decompiler-confusion techniques (deliberately malformed exception ranges, corrupted attribute lengths) specifically because it cannot change observable behaviour: every path still terminates exactly as before, and an escaping exception still propagates exactly as before. It only adds a control-flow shape — a handler covering an entire method body with no locally-visible reason to exist — that common decompilers' control-flow-to-source reconstruction tends to mishandle or render unreadably.

Where it sits in the pipeline

Applied once nativization decisions are already final, directly to whatever's left as ordinary bytecode — never to a method about to be nativized, since a nativized method has no Code attribute at all for a decompiler to see in the first place, and wrapping it first would only add an unnecessary nested-exception-handler shape the translator doesn't need to deal with.

Threat model

Purely a decompiler-output-quality attack, not a logic change and not a runtime protection — it doesn't detect anything or fail anything closed. Its only job is making the decompiled source of a non-nativized method harder to read correctly.

Verified. Every wrapped class in a real, protected Apache Commons Exec build loads and verifies cleanly under full JVM bytecode verification (triggered via Class.forName across every output class, not just the ones directly exercised by a test), with javap -v confirming a correctly-typed StackMapTable entry at each injected handler.
