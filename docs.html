Getting started

Status. RJNI has not yet shipped a packaged, publicly installable build. Everything on this page describes the tool's actual, verified pipeline and its intended external interface — not a binary you can currently download. To discuss early access, contact hello@rjni.dev.

Once packaged, RJNI is designed to run as one extra step after your normal build, against an already-built JAR — it does not otherwise change your build process:

rjni protect --in build/libs/app.jar --out build/libs/app-protected.jar

The output is a drop-in replacement JAR: same entry point, same public behaviour. It runs on an ordinary JVM. Nothing about how you deploy or launch it changes. Optional flags for trial mode, keep rules, and watermarking are covered under Configuration.

How it works

RJNI runs six stages over your JAR, in this order, every time:

  1. Input and configuration — the JAR, an optional trial fraction, optional keep patterns, an optional watermark.
  2. Parsing and eligibility scan — every class is checked against the exclusion-profile registry and an interface check.
  3. Bytecode-level protection passes — class renaming, string encryption, method/field renaming, control-flow flattening, each an independent pass over the same class set.
  4. Per-method translation — every remaining method body is exported to an intermediate representation and checked for translatability.
  5. Native compilation and JNI relinking — translatable methods are compiled into one shared native library and bound via RegisterNatives.
  6. Finalisation and packaging — decompiler-resistant wrapping, anti-tamper checksums, anti-debug injection, resource encryption, watermark embedding, obfuscated native-library bundling, and runtime-class renaming, in that order, before the output JAR is written.

A method that can't be safely translated is excluded with a specific, reported reason — never silently mistranslated and never left to crash at runtime. See Known limitations for the current list of excluded shapes.

Protection passes reference

Every pass below has been verified against real, unmodified third-party JARs — including a six-project open-source corpus and a real, independent 1,200-class application — not only against hand-built test fixtures.

Method nativization

Implemented Eligible method bodies are translated to a Rust intermediate representation, compiled into the JAR's shared native library, and bound to the class through JNI's RegisterNatives. The method is flipped to native and its Code attribute is removed entirely — there is no bytecode body left for a decompiler to reconstruct.

Class name obfuscation

Implemented Every eligible class is renamed into one flat, opaque package using a constant-pool-aware bytecode remapper, which correctly rewrites every reference to it — descriptors, signatures, inner-class metadata, annotation values, and stack-map frames. A class referenced only by a String constant (Class.forName, a ServiceLoader provider file) is excluded from renaming, since a bytecode remapper cannot see, and therefore cannot safely rewrite, that reference.

Method & field renaming

Conditional Private methods and fields are always renamed — a private member cannot be inherited or referenced from outside its declaring class, so there is no dispatch ambiguity to resolve. Non-private, non-static instance members are also renamed, but only where the member's entire ancestor chain — every superclass and interface, recursively — resolves to classes inside the JAR being protected. A class with any external supertype (a JDK class, a third-party library type) keeps the conservative, private-only slice, since renaming it could silently break dispatch from code this pass can't see. static members are never renamed by this pass, and neither is any member of java.lang.Object's own instance-method surface (equals, hashCode, toString, and so on).

String & constant encryption

Conditional Every LDC of a String literal inside a method body is replaced with a per-string, position-keyed obfuscated payload and a runtime decrypt call resolved at the point of use. This runs before nativization in the pipeline, so a nativized method's compiled native code never embeds the plaintext either — it calls back into the same decrypt routine. A static final String field's own compile-time constant value is not covered: other classes may already have inlined that plaintext into their own constant pool at their own compile time, a copy this pass has no way to reach.

Control-flow flattening

Conditional Rewrites a method's branches, jumps, and fall-through into a single dispatcher table, without physically reordering blocks. Excluded: constructors, any method with an existing exception handler, and — verified by a real dataflow analysis before flattening is attempted — any method where a value crosses a block boundary on the operand stack rather than through a local variable (a common shape for a ternary expression used directly as an argument). These are conservative exclusions, not silent failures.

Decompiler-resistant wrapping

Implemented Every remaining, non-constructor method body is wrapped in a whole-method catch (Throwable t) { throw t; }. This cannot change observable behaviour — every path still terminates exactly as before — but introduces a control-flow shape that common decompilers' structured-code reconstruction tend to mishandle or render unreadably.

Anti-tamper checksums

Implemented Every protected class's static initialiser verifies its own current bytes against a SHA-256 checksum computed at protect-time and stored in a separate bundled resource, throwing before any of the class's own initialisation runs if the bytes don't match. This detects a class file edited in isolation after protection — the common naive-patch pattern — not an attacker who edits the checksum resource and the class together, or who modifies a running JVM directly.

Anti-debug detection

Conditional Every protected class's static initialiser also checks for the standard JDWP debug-agent startup flags (-agentlib:jdwp, -Xrunjdwp) and fails loudly if found. This is deliberately narrow: it does not treat a general -javaagent as a signal, since production JVMs commonly run legitimate APM or monitoring agents, and flagging those would be a damaging false positive against your own production deployment.

Resource & asset encryption

Conditional Every Class#getResourceAsStream/ClassLoader#getResourceAsStream call site is redirected through a runtime loader that transparently decrypts a resource if, and only if, it was encrypted at protect-time — otherwise it's a pure pass-through, so rewriting every call site is always safe. A resource is only encrypted where a literal, statically resolvable path argument positively attributes it to a call site inside the protected class set. The URL-returning getResource form is not covered.

Native library bundling

Implemented The compiled native library is stored at a random, per-build path with a .dat extension and obfuscated before bundling, so the raw bytes carry no recognisable native-binary header and the bundled artefact's path isn't identical across every RJNI-protected jar. This raises the bar against a casual scan for a bundled native library; it does not resist an attacker who reads this exact scheme and reimplements the reversal.

Loader & runtime class hardening

Implemented RJNI's own bundled bootstrap classes — the native loader, string decryptor, tamper check, and their siblings — are renamed per build into their own flat package, rather than shipping under a fixed, well-known name. The one exception is a small, fixed manifest location every protected jar shares, since some starting point has to be predictable for the loader to find its own configuration.

Build-time watermarking

Implemented An optional per-build identifier — typically per-licensee — is embedded, obfuscated the same way the native library is, and can be recovered from a jar file directly (reading the jar's own entries, not by running its bytecode) for tracing a leaked copy back to whoever it was issued to.

Config-driven keep rules

Conditional Class-level patterns — an exact class, a package and every subpackage (pkg.**), or the direct members of one package (pkg.*) — exclude matching classes from renaming entirely. Member-level keep rules (preserving specific fields or methods within an otherwise-renamed class) are not yet supported.

Trial / evaluation mode

Implemented Protects a deterministic subset of eligible classes — selected by sorted internal name, not at random — so a trial run on the same input always produces the same output. Every unselected class is written through byte-identical to the input.

Compatibility & exclusions

See the homepage Compatibility section for the full table. In summary: class file major versions 52 through 70 (JDK 8 through JDK 26), verified against a six-project open-source corpus spanning every in-scope JDK LTS release. Framework exclusion profiles cover reflection-by-name, ServiceLoader, JPMS module descriptors, Spring's own proxy internals, and the packaged internals of CGLIB, ByteBuddy, Javassist, and Hibernate's bytecode provider.

Not yet covered: bitwise/shift operators, switch statements, unary negation, multi-dimensional array literals, block-level synchronized, object reference-equality branches, and StringConcatFactory-based string concatenation. A method using one of these is cleanly excluded from nativization with a specific reason, not mistranslated.

Configuration

Three optional controls, layered on top of the default full-protection run:

rjni protect --in app.jar --out app-protected.jar \
  --trial 0.2 \
  --keep keep-rules.txt \
  --watermark "customer-42"

Trial fraction (--trial) protects a deterministic fraction of eligible classes instead of the whole jar, for evaluation before a full licence.

Keep rules (--keep) point at a plain-text file, one glob per line, blank lines and # comments ignored:

# exact class
com.example.plugins.PluginApi

# a package and every subpackage
com.example.plugins.**

# only the direct members of one package
com.example.internal.*

Watermark (--watermark) embeds a per-build identifier, recoverable later from the output jar's own entries without running it.

Build integration

Today, RJNI runs as a JVM application against an input and output JAR path, invoked as one step in a build pipeline. A packaged, standalone CLI binary, and build-tool plugins for Gradle and Maven, are planned but not yet shipped — see the status callout under Getting started. Code signing (Authenticode on Windows, notarization on macOS) is not required by RJNI's architecture: the output is a library loaded in-process via System.load() from already-running JVM code, never a shell-launched executable, so the launch-time "unverified developer" gate those mechanisms exist to satisfy doesn't apply. The one real, user-fixable exception is macOS's quarantine attribute on a jar downloaded through a browser, which can propagate to the extracted native library on first load — resolved with a right-click-then-Open, or xattr -d com.apple.quarantine on the jar.

Security model

See the homepage Security model and limitations section for the full adversary-tier table and the plainly stated list of what RJNI does and does not claim to defend against. In short: RJNI is built to raise the cost of casual and moderately motivated reverse engineering. It explicitly does not claim to defeat a determined attacker with a disassembler, native-code expertise, and time against the compiled native library.

Known limitations

Documented directly, not left implicit:

  • A nativized method's exact name and JVM descriptor are structurally visible as plaintext inside the compiled native library — RegisterNatives is a name-based JNI API, and there's no way around that without abandoning JNI as the relinking mechanism entirely.
  • A class with any external (JDK or third-party) supertype or interface only receives the conservative, private-members-only renaming slice.
  • A handful of bytecode shapes — listed under Compatibility — are not yet translated, and are cleanly excluded rather than mistranslated.
  • Multi-release JAR variant handling and Windows delete-on-close cleanup for the extracted native library are designed but not yet implemented.
  • Layering RJNI's output with another obfuscator (or protecting another obfuscator's output) is not verified in either direction.
